# Обновление одним скриптом

Из корня проекта:

```bash
./scripts/deploy.sh --check  # тесты и сборка, сервер не используется
./scripts/deploy.sh          # проверка + обновление root@192.168.1.206
```

При первом использовании нужны локальные Python 3.11+ с модулем venv, Node.js/npm, OpenSSH, tar, sha256sum и доступ к реестрам pip/npm. Python-зависимости автоматически устанавливаются во временное окружение; `npm ci` использует зафиксированный package-lock.json. Исходники и локальный node_modules не меняются. Для ускорения можно передать `PYTHON=/absolute/path/to/venv/bin/python` с установленным `backend/requirements-dev.txt`.

## SSH без пароля в скрипте

Один раз настройте ключ и проверьте отпечаток сервера при первом подключении:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/pact_deploy
ssh-copy-id -i ~/.ssh/pact_deploy.pub root@192.168.1.206
ssh-add ~/.ssh/pact_deploy
ssh -i ~/.ssh/pact_deploy root@192.168.1.206 true
DEPLOY_IDENTITY="$HOME/.ssh/pact_deploy" ./scripts/deploy.sh
```

Для ключа с парольной фразой требуется ssh-agent с загруженным ключом. Скрипт использует BatchMode и StrictHostKeyChecking=yes: не спрашивает и не хранит пароль сервера, не принимает неизвестный ключ автоматически. SSH-алиас можно задать как `DEPLOY_HOST=pact-server`. Альтернативный файл настроек: `DEPLOY_SSH_CONFIG=/путь/к/config`. Если системный SSH-конфиг сообщает об ошибке владельца/прав, можно использовать `DEPLOY_SSH_CONFIG=/dev/null` и явно передать ключ.

## Что делает обновление

1. Создаёт неизменяемый локальный снимок исходников, запускает backend-тесты, тесты deploy-транзакции и frontend-тесты, собирает интерфейс.
2. Передаёт только runtime-код, шаблоны, готовый frontend и скрипты. Исходные документы клиентов, .env, базы, node_modules и тестовые данные в пакет не попадают.
3. Проверяет SHA-256 пакета. Подготавливает `/opt/pact/releases/<дата-хеш>` и отдельное Python-окружение, пока прежнее приложение работает.
4. Останавливает запись, сохраняет базу и документы в `/var/backups/pact/<дата-хеш>`, проверяет контрольные суммы.
5. Переключает `/opt/pact/backend`, `frontend`, `templates`, `scripts` и `.venv` на новый выпуск через ссылки. Исходная установка с обычными каталогами поддерживается: прежние пути перемещаются в `<дата-хеш>.previous`.
6. Запускает pact и проверяет API с подключением к БД, главную страницу и доступность JS/CSS. При сбое возвращает прежние пути и перезапускает старую версию. Если откат тоже не проходит проверку, сообщает об этом и завершается с ошибкой.

База и `/var/lib/pact/documents` не заменяются при откате. Изменения схемы БД требуют отдельной процедуры миграции: этот скрипт не делает обратных миграций. Nginx, сертификаты, `/etc/pact.env` и systemd unit приложения не заменяются.

Обновление выполняется системной службой `pact-deploy-<дата-хеш>`, чтобы разрыв SSH не прервал переключение файлов. При потере связи не запускайте повторно вслепую: проверьте состояние сервиса и журнал на сервере:

```bash
systemctl list-units 'pact-deploy-*' --all
journalctl -u 'pact-deploy-*' --since today
systemctl status pact
```

На время копирования данных и перезапуска возможна недоступность сайта. Параллельные deploy/backup блокируются flock. Ежедневный таймер копирования временно приостанавливается и затем возвращается в прежнее состояние. Старые выпуски и копии автоматически не удаляются: контролируйте свободное место. После аварийного выключения сервера во время переключения может потребоваться ручное восстановление из каталога `.previous`.

## Изменение шаблонов

Побайтовое отличие рабочих DOCX от серверных блокирует обновление до явного подтверждения проверки:

```bash
./scripts/deploy.sh --templates-reviewed
```

Используйте флаг только после генерации контрольных DOCX/PDF и просмотра всех страниц. Сам скрипт проверяет целостность шаблонов, но не заменяет визуальную проверку.

## Проверка самого скрипта

```bash
bash -n scripts/deploy.sh scripts/deploy-remote.sh scripts/backup-native.sh
python3 scripts/tests/test_deploy.py
```

Три теста выполняются в временном каталоге с имитацией systemd/PostgreSQL: успешное переключение, сбой backup, неуспешная проверка новой версии с откатом. Рабочий сервер ими не затрагивается.

## GitHub Actions

`.github/workflows/ci.yml` проверяет pull request и push в `main` на GitHub-hosted Ubuntu, Python 3.11 и Node.js 22. Используется тот же `deploy.sh --check --output DIRECTORY`: backend/deploy/frontend tests, TypeScript/Vite build и runtime archive. Приложение собирается один раз; отдельная job скачивает этот же artifact, подписывает архив Cosign через GitHub OIDC и публикует release `ci-<run_id>-<attempt>-<commit12>`. Ручной запуск Actions из `main` также создаёт выпуск. Ветки и PR не имеют разрешений выпуска или подписи.

Сайт забирает готовый пакет из публичного GitHub Release. Ключи, пароли GitHub, Actions runner внутри LAN и открытие входящих портов не требуются. Подпись проверяется по точному workflow identity `https://github.com/garooduh/pactum/.github/workflows/ci.yml@refs/heads/main` и issuer `https://token.actions.githubusercontent.com`. SHA256SUMS служит дополнительной диагностикой, но не заменяет подпись. Только архив после успешной проверки становится источником remote installer.

### Первоначальная установка updater в контейнере сайта

Выполняется root из проверенной копии исходников:

```bash
bash scripts/install-cosign.sh
install -m 755 scripts/pull-deploy.py /usr/local/sbin/pact-pull-deploy
install -m 644 deploy/pact-update.service deploy/pact-update.timer /etc/systemd/system/
systemctl daemon-reload
systemd-analyze verify /etc/systemd/system/pact-update.service /etc/systemd/system/pact-update.timer
# Первый запуск — после сверки рабочего кода и DOCX с выпускаемыми исходниками.
systemctl start pact-update.service
systemctl enable --now pact-update.timer
```

Cosign v3.1.4 Linux amd64 проверяется по фиксированной SHA256 при установке. Загрузки идут через GitHub Releases asset API. Updater и verifier принадлежат root и не обновляются автоматически из runtime release. При изменении этих файлов администратор повторяет установку из проверенных исходников.

Timer проверяет GitHub каждые пять минут с небольшим случайным сдвигом. Новая установка включает существующую транзакцию backup/symlink/rollback. Перед ней проверяется `nginx -t`; health проверяет systemd, локальные API/JS/CSS и HTTPS через внешний Nginx по LAN-адресу `192.168.1.11`, сохраняя домен `pactum.qbob.ru` для Host/SNI и проверки сертификата. Это обходит отсутствие NAT loopback на маршрутизаторе без изменения DNS; доступность снаружи сети проверяется отдельно. Секреты, Nginx, сертификаты, БД и выпущенные документы не входят в release. Схема БД автоматически не мигрируется.

Состояние `/var/lib/pact-deploy/state.json` фиксирует последний установленный tag и commit. Порядок `(run_id, attempt)` запрещает повторную установку и downgrade. Провалившийся tag не запускается повторно каждые пять минут. Остальные новые выпуски могут устанавливаться; после исправления причины разрешён явный повтор:

```bash
journalctl -u pact-update.service -n 100 --no-pager
systemctl list-units 'pact-deploy-*' --all
/usr/local/sbin/pact-pull-deploy --retry
```

Если изменены DOCX, сначала создайте QA-документы и визуально проверьте их, затем для текущего последнего выпуска:

```bash
/usr/local/sbin/pact-pull-deploy --retry --templates-reviewed
```

Флаг не сохраняется для будущих выпусков. Первый выпуск с побайтово идентичными production-шаблонами не требует повторного одобрения шаблонов.

Остановить автоматическую проверку:

```bash
systemctl disable --now pact-update.timer
```

Уже начатая установка работает отдельной службой, чтобы потеря SSH или остановка updater не прерывали backup/rollback. Перед ручным вмешательством проверьте `pact-deploy-*`. Для аварийного возврата сначала остановите timer, затем используйте сохранённые release paths и backup по штатному плану; marker не сбрасывается автоматически. Проверки транзакции и updater без обращения к серверу:

```bash
python3 -m unittest discover -s scripts/tests -p 'test*.py' -v
```

Настройки репозитория должны разрешать Actions. Разрешения записи выдаются явно только release job. Изменение workflow или кода в `main` даёт возможность обновить production, поэтому доступ записи в `main` следует выдавать только доверенным участникам.

После сетевого сбоя публикации можно использовать Re-run failed jobs: tag берётся из metadata первоначального пакета, неполный draft дополняется, опубликованный архив не перезаписывается. Re-run all jobs создаёт пакет с новым номером attempt. Проверка текущего публичного HTTPS также выполняется из GitHub после публикации; её сбой не блокирует выпуск, который может быть нужен для восстановления сайта. Фактическое завершение установки проверяется на сервере по `pact-update.service` и state.json; зелёный Actions означает успешную сборку и публикацию, а не подтверждение установки.

### Миграция списков мебели (v2)

Перед первым запуском новой версии нужна штатная резервная копия БД и DATA_DIR.
Startup вызывает явную идемпотентную аддитивную миграцию
`backend/app/furniture_migration.py`: создаёт furniture_lists,
furniture_catalogs, furniture_issues и marker schema_version=2. Колонки прежних
таблиц и договоры не изменяются. Повтор после частичного создания безопасен.
Откат: переключить прежний release штатным механизмом, сохранив новые таблицы,
marker и файлы; обратная миграция и удаление данных не требуются. Восстановление
backup — только отдельным решением при повреждении данных.
Начальный каталог и PNG входят в backend runtime archive. Загрузки каталога и
выпуски находятся внутри существующего DATA_DIR и входят в текущие backups.

Импорт XLSX требует отдельного location `/api/furniture/catalog` с
`client_max_body_size 20m` на обоих Nginx (внешнем и в LXC). Образцы deploy/
обновлены; runtime release конфигурацию Nginx не устанавливает. Перед включением
импорта применить этот location вручную с сохранением proxy headers, проверить
`nginx -t` и выполнить reload. Для остальных запросов оставить лимит 1 МБ.

Установщик Cosign при сетевых сбоях чередует официальный asset API с обходом
устаревшего кеша и официальный URL release v3.1.4. Оба пути проверяются по одной
закреплённой SHA-256; непроверенные байты не устанавливаются. Это не меняет
версию verifier, identity workflow или проверку подписи пакета на сервере.

### Нумерация списков мебели (v3)

Перед первым запуском остановить запись и сделать штатную согласованную
резервную копию PostgreSQL и DATA_DIR, проверить успешность backup.
Startup явно вызывает идемпотентную миграцию furniture_migration.py:
добавляет number, created_at, уникальный индекс, furniture_counter и marker 3.
Существующие списки получают номера 1…N по названию без учёта регистра
(Ё = Е), затем UUID; created_at остаётся NULL. Ревизии, JSON и файлы не меняются.
Миграция выполняется до обработки HTTP-запросов; на PostgreSQL блокирует таблицу
списков на время нумерации. Предусмотреть короткую недоступность при запуске.

Откат к прежнему коду: штатно переключить release, сохранив обе добавленные
колонки, индекс, счётчик и markers. Не удалять их и не уменьшать счётчик.
Прежний код игнорирует новые поля; созданные им списки имеют NULL в новых
колонках. При возврате новой версии повторная миграция присвоит им номера
выше сохранённого максимума, дата останется неизвестной. Существующие номера
сохранятся. Восстановление backup требует отдельного решения, поскольку
заменит более новые пользовательские данные; обратная миграция не нужна.
